<Lede>
  Peer-to-peer has one honest cost: two devices have to be awake at the same
  time to converge. A **host** is the answer that keeps the premise intact —
  one more of *your* devices, with no screen, running on a machine that never
  sleeps. **It is a replica, not a server.** It holds what your laptop holds,
  under the same identity, and nobody else can read it either.
</Lede>

<h2 id="what">What it is</h2>

`tasfer host` runs the app without the app: the same document model, the same
CRDT, the same wire protocol — wired to Node's SQLite and sockets instead of a
browser's. You link it the way you link a phone, and from then on it is one of
your devices. Close the laptop mid-sentence; the host already has the sentence,
and your phone gets it from there.

What that buys you:

- **Convergence without a rendezvous.** Devices sync through a peer that is always up, instead of waiting to overlap.
- **A copy that is yours.** A backup you can `tar` and restore, on hardware you picked.
- **Nothing new to trust.** It is enrolled under your identity like any other device — not an account, not a service, not a third party.

<Callout kind="warn" title="A host is the account.">Linking hands the machine your root identity and every space, personal ones included. Run it somewhere only you can reach: your own box, full-disk encrypted, not a shared shell.</Callout>

<h2 id="install">Install</h2>

Each release publishes a self-contained build per platform — the host, and the
two native modules it loads beside itself. Nothing else is required: no Node,
no toolchain, no clone.

```bash
curl -fsSL https://tasfer.app/install.sh | sh
```

That reads the releases, picks the newest one carrying a build for your machine,
checks it against the release's `tasfer-checksums.txt`, and unpacks it to
`~/.local/lib/tasfer` with a `tasfer` link in `~/.local/bin`. Nothing needs root,
which is the point: `tasfer update` later writes to a directory you already own.

Builds are published for macOS and Linux, on arm64 and x64, with
[each release](https://github.com/tasferlabs/tasfer/releases) — beside the
desktop installers, since the host ships at the app's version from the app's own
release.

The script takes a few knobs, as flags or as environment variables:

<PropsTable cols={["Setting", "Default", "Description"]} rows={[
  { name: "--version / TASFER_VERSION", type: "newest", desc: "Install a specific version instead of the newest one that has a build for this platform." },
  { name: "--install-dir / TASFER_INSTALL_DIR", type: "~/.local/lib/tasfer", desc: "Where the build is unpacked. The directory moves as a unit — `tasfer` loads `node_modules/` from beside itself, and a binary separated from them cannot open a database." },
  { name: "--bin-dir / TASFER_BIN_DIR", type: "~/.local/bin", desc: "Where the `tasfer` symlink goes. The script says so if it is not on your PATH." },
]} />

For a system-wide install — the one a systemd unit under its own user wants —
download it first and run it with the rights it will need:

```bash
curl -fsSL https://tasfer.app/install.sh -o install.sh
sudo TASFER_INSTALL_DIR=/opt/tasfer TASFER_BIN_DIR=/usr/local/bin sh install.sh
```

<Callout kind="note" title="Or do it by hand.">Every archive and its `sha256` line sit on the [releases page](https://github.com/tasferlabs/tasfer/releases): `tasfer-<version>-<platform>-<arch>.tar.gz` beside `tasfer-checksums.txt`. Unpack one wherever you like — the script does nothing you cannot do with `curl` and `tar`.</Callout>

<Callout kind="note" title="Or build it from the repo.">Node 22 or newer, then `npm install && npm run build` in `apps/cli` — `npm link` puts `tasfer` on your PATH. A source build updates with `git pull`, not with `tasfer update`.</Callout>

`node-datachannel` is one of the two modules in the archive: with it, the host
makes direct WebRTC connections like every other device. On a platform with no
prebuilt binary the host still syncs, over the relay path the app already falls
back to. Everything is encrypted before it leaves the machine either way.

<h2 id="update">Keep it up to date</h2>

```bash
tasfer update           # replace this install with the newest release
tasfer update --check   # just say what is available
```

It reads the published releases, downloads the build for this platform, checks
it against the release's `tasfer-checksums.txt`, and swaps it into place — refusing
rather than installing anything whose checksum does not match. A running host
keeps running on the old build; restart it to pick the new one up.

Updating writes to the directory the binary lives in, so it needs the rights
that installed it. The default install is under your home directory and needs
none; a system-wide one wants `sudo tasfer update`.

<h2 id="link">Link it to your account</h2>

<Steps>
  <Step title="Get a code from the app">
    On a device you already use, open **Profile → Link a device** and copy the code.
  </Step>
  <Step title="Hand it to the host">
    ```bash
    tasfer host link <code> --name "basement box"
    ```
    Keep the app open until it says the link is done — the two have to meet.
  </Step>
  <Step title="Run it">
    ```bash
    tasfer host
    ```
    The host is now online and syncing. `tasfer host status` says what it holds.
  </Step>
</Steps>

You can also start from the host: `tasfer host invite` prints a code to paste
into the app's **Enter a code from another device**. Same handshake, opposite
direction.

<Callout kind="note" title="One process at a time.">Every command opens the same database. Stop the running host before linking, so pairing is not rewriting an identity a replica is mid-sync under.</Callout>

<h2 id="service">Keep it running</h2>

The host is a plain foreground process that stops on `SIGINT`/`SIGTERM`, so any
supervisor will do. A systemd unit:

```ini
[Unit]
Description=Tasfer host
After=network-online.target

[Service]
ExecStart=/usr/local/bin/tasfer host
Restart=on-failure
User=tasfer

[Install]
WantedBy=multi-user.target
```

<h2 id="backup">Back it up</h2>

```bash
tasfer export                    # every space, to tasfer-export-<date>.zip
tasfer export backup.zip         # or a name you pick
tasfer export --space "Work"     # just one of them
```

The archive is the one the app's **Export all** writes, from a machine with no
app: a folder per space, a markdown file per page, and one `images/` folder the
pages link into. Nothing in it needs Tasfer to read — it is markdown on disk —
and the app imports it straight back into any space, on any device.

Which makes a scheduled backup a one-liner:

```
0 4 * * *  tasfer export --out /backups/tasfer-$(date +\%F).zip
```

<Callout kind="note" title="An export is the portable copy, not the exact one.">It carries pages and images — not the operation log, not this device's identity. Importing it back makes new pages rather than restoring this host. For the exact copy, stop the host and take the data directory: `tasfer.db` and the asset files beside it. That one is still this device, already linked.</Callout>

<Callout kind="note" title="What a host does not add.">No accounts, no server-side rendering, no API. It cannot read a space it was never invited to, and it holds no key your other devices do not.</Callout>
