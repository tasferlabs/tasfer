<Lede>
  The schema declares what your document is made of. Extend it to add new block
  types (*nodes*) such as a callout block, and inline formatting (*marks*) such
  as an @-mention or a highlight.
</Lede>

The editor follows the famous block methodology that was popularised by Notion and markdown. If you have been living under a rock, this is just a way to build a document out of blocks: every paragraph, heading, image or table is its own block, stacked from top to bottom.

<h2 id="node">node (blocks)</h2>

A node is a block type. It declares its attributes (fields synced through the [CRDT](/docs/editor/concepts#crdt)), how it is saved, and how it is drawn.

There are several ways to define a node. Use the one that fits your use case.

The shortest is `defineNode`. A callout box:

```ts
import { defineNode } from "@tasfer/editor";

const callout = defineNode("callout", {
  // Attributes: each one is synced and has a default.
  attrs: { tone: { default: "note" } },
  // How the built-in box renderer paints it.
  render: {
    background: "rgba(29,185,132,0.10)",
    borderLeft: { width: 3, color: "#1db984" },
    label: (block) => `Callout (${block.tone})`,
  },
});
```

It is saved to markdown as a generic `<x-callout tone="…" />` tag, so you do not write a parser.

{/* TODO needs an engine change first: `render` only takes an object today. Uncomment once it can be a function.
As you saw in the earlier example, there were two properties you defined to create a custom node, but you could also replace the render object with a function that takes in the canvas context. */}

The other way is to use a class. Subclass a node and register the instance directly. The class owns its drawing, strings, and UI, and `static nodeConfig` takes the same attrs as `defineNode`. Both ways produce the same data, so you can switch between them:

```ts
import { AtomicNode, baseSchema } from "@tasfer/editor";

class CalloutNode extends AtomicNode {
  readonly type = "callout";
  static nodeConfig = { attrs: { tone: { default: "note" } } };

  protected intrinsicHeight() {
    return 48;
  }
  protected draw(box, c) {
    c.ctx.fillStyle = "rgba(29,185,132,0.10)";
    c.ctx.fillRect(box.x, box.y, box.width, 48);
  }
}

const schema = baseSchema.extend({ nodes: [new CalloutNode()] });
```

You can also look at the [reference](/docs/editor/api-schema#definenode) for more details.

<h3 id="nested-caret">A caret inside a node's own content</h3>

Most nodes, such as the text node, hold their text in the block, and the caret points at it by index. Not all nodes can do that. A table keeps its cells in a structured attachment, a separate tree stored next to the block (see [tables](/docs/editor/api-schema#table)). There is no index there, so the node handles the caret itself, in both directions:

```ts
class GridNode extends Node {
  contentSelectionFromPoint(layout, local, c) {
    const cell = cellAt(layout, local.x, local.y);
    if (!cell) return null;
    const point = {
      kind: "text",
      blockId: c.block.id,
      contentId: cell.contentId,
      nodeId: cell.id,
      field: "text",
      afterCharId: charBefore(cell, local.x),
      affinity: "forward",
    };
    return { anchor: point, focus: point };
  }

  contentCaretRect(layout, point, c) {
    if (point.kind !== "text") return null;
    const cell = cellById(layout, point.nodeId);
    if (!cell) return null;
    return {
      x: c.origin.x + cell.x + widthUpTo(cell, point.afterCharId),
      y: c.origin.y + cell.y,
      height: cell.textHeight,
    };
  }
}
```

The first hook turns a click into an address (a `ContentPoint`). The second turns that address back into the place to draw the caret. Skip the second and the caret is never painted.

`cellAt`, `charBefore` and the others are your own layout code. Add `c.origin`, the block's top-left, to what you return.

{/* `c.origin` is the block's top-left in whichever space the caller works in (viewport when painting, document when scrolling the caret into view), so return the rect relative to it and both callers get what they need. Returning `null` — or leaving `contentCaretRect` unset, as every built-in node does — keeps the ordinary text-caret path. */}

{/* Implementing the hook is also what makes the engine _paint_ a caret in a block that has no flat text of its own. Both cursor paths otherwise stop at blocks the schema marks as textual; a node that declares `contentCaretRect` is admitted past that gate, and `editor.view.coordsAtContent(point)` starts returning coordinates for the same point instead of `null`. Core never names the block type — the node's own hook is the credential. */}

**Caret height.** Return the text height (ascent + descent), starting at the top of the line. The full line height is taller, and your caret would stick out next to the one in a paragraph.

**A selected range.** For a range inside your content, add `contentSelectionGeometry`. It returns the highlighted band and its two ends:

```ts
contentSelectionGeometry(layout, selection, c) {
  return {
    rects: [/* the band, relative to c.origin */],
    start: { x, y, height },
    end: { x, y, height },
    isForward: true, // the anchor is the start
    opacity: 0.4,    // optional: how strongly you fill the band
  };
}
```

With it, phones show selection handles on the range and let you drag them, a tap on the band counts as touching the selection, and a mouse can drag the selected text out. Without it there are no handles, and a tap collapses the range.

If your content takes some pieces whole (a formula's √), a handle crossing such a piece shades the covered part, and the piece joins the range once the finger is past its middle. The shade uses the theme's `selection.opacity`. Return `opacity` when your node fills its band at another strength, so the two look like one highlight.

**Collaborators.** A peer's caret in your content is placed with the same `contentCaretRect`, so you write nothing extra. Their selection is yours to paint. In `paint`, loop over `decorationsForBlock(state.ui.decorations, block.id)` and pass your rects to `paintDecorationRects(ctx, rects, deco, styles)`. It draws the fill or the underline, whichever the [decoration](/docs/editor/api-editor#decorations) asks for. Give each rect a `baseline` so an underline sits under the text. For a box with no text, build the rect with `boxDecorationRect(box, deco)`.

**Text.** To draw and measure text the way paragraphs do (marks, Arabic, formulas, IME), use the engine's own helpers such as `paintTextRun` and `layoutText`. See [Text inside a custom node](/docs/editor/api-schema#text-helpers).

<h3 id="document-edge">Leaving a node at the document's edge</h3>

A node without text has no place for a caret above or below it. So when your node is the first or last block, the editor adds an empty paragraph next to it when the user clicks the blank space there, or presses ArrowUp/ArrowDown or PageUp/PageDown. A document with only your node is never a dead end.

Custom nodes get this for free.

The one exception is a node with a [nested caret](#nested-caret). While the caret is inside your content, your node handles the arrow keys. So when the caret runs out of rows, hand it on yourself:

```ts
import {
  appendTrailingParagraph,
  prependLeadingParagraph,
} from "@tasfer/editor";

const edge = appendTrailingParagraph(state, block);
if (edge.kind === "break") return { state: edge.state, ops: edge.ops };
```

Both helpers return `{ kind: "fallthrough" }` when the schema allows no paragraph there. Leave the caret where it is in that case.

<h3 id="enter">Enter and Shift+Enter</h3>

Enter dispatches `SPLIT_BLOCK`, and Shift+Enter dispatches `EXIT_BLOCK`. A text node needs nothing: both split the block like a paragraph.

A node with several lines of its own should keep Enter for its lines and use `EXIT_BLOCK` to leave. Create the paragraph with `insertParagraphBeside`. It takes care of the position, the schema rules and the caret:

```ts
import { EXIT_BLOCK, insertParagraphBeside } from "@tasfer/editor";

bus.registerState(EXIT_BLOCK, (state) => {
  const blockIndex = state.document.cursor?.position.blockIndex ?? -1;
  if (state.document.page.blocks[blockIndex]?.type !== "callout") return;
  // side: "after" | "before"; caret: "new" moves into the paragraph, "keep" stays
  const result = insertParagraphBeside(state, blockIndex, "after", "new");
  return result
    ? { ...result, handled: true }
    : { state, ops: [], handled: true }; // the schema allows no paragraph here
});
```

If text was selected, it is already deleted when your handler runs. You only ever see a caret.

<h3 id="expand-selection">Expand selection</h3>

Expand selection (⌃⇧⌘→ on Apple, Shift+Alt+→ elsewhere) grows the selection one step per press: word → block → document. The same keys with ← shrink it back.

A node with its own structure can add steps before these. Handle `EXPAND_SELECTION_STEP`, list every range you could select around the current one, and let `nextEnclosingRange` pick the smallest one that is wider:

```ts
import {
  EXPAND_SELECTION_STEP,
  nextEnclosingRange,
  selectFlatRange,
} from "@tasfer/editor";

bus.registerState(
  EXPAND_SELECTION_STEP,
  (state) => {
    const caret = state.document.cursor?.position;
    const block = caret && state.document.page.blocks[caret.blockIndex];
    if (block?.type !== "callout") return;
    const current = { from: caret.textIndex, to: caret.textIndex }; // or the selected range
    const next = nextEnclosingRange(myRanges(block, current), current);
    if (!next) return; // selected whole: let the engine take the document
    return {
      state: selectFlatRange(state, caret.blockIndex, next.from, next.to),
      ops: [],
      handled: true,
    };
  },
  50,
);
```

Shrinking needs no code. The engine remembers the steps it took.

A node with a nested caret selects through its own content selection instead of `selectFlatRange`. The built-in math, code and table nodes are good examples to read.

<h2 id="strings">Localized strings</h2>

A node keeps the text it paints (labels, prompts) in a `strings` object with English defaults. Read one inside `draw` with `this.str(state, key)`.

The editor ships no i18n library. The host translates through `theme.nodeStrings`, keyed by block type and then by your string key:

```ts
class CalloutNode extends AtomicNode {
  readonly type = "callout";
  readonly strings = { hint: "Add a note…" };

  protected draw(box, c) {
    c.ctx.fillText(this.str(c.state, "hint"), box.x + 12, box.y + 24);
  }
}

createEditor({
  element,
  schema,
  theme: { nodeStrings: { callout: { hint: "ملاحظة…" } } },
});
```

<h2 id="overlays">Node-owned UI (overlays)</h2>

A node can ask the host to show real UI over one of its blocks, such as a popover or an inline editor. The node does not render it. `overlays()` returns plain data: a `key`, the block id and a `rect`.

```ts
class CalloutNode extends AtomicNode {
  readonly type = "callout";
  overlays(c) {
    // Only while this block holds the caret.
    if (c.state.document.cursor?.position.blockIndex !== c.blockIndex)
      return [];
    return [
      {
        key: "callout-editor",
        blockId: c.block.id,
        rect: { x: c.origin.x, y: c.origin.y, width: c.maxWidth, height: 48 },
      },
    ];
  }
}
```

Use the block id, not the index. Indexes shift when someone else edits.

The host maps each `key` to a component and mounts it at the `rect`, every frame:

```tsx
const OVERLAYS = { "callout-editor": CalloutEditor };

editor.host.collectOverlays().forEach((o) => {
  const Comp = OVERLAYS[o.key];
  if (Comp) mountAt(o.rect, <Comp overlay={o} editor={editor} />);
});
```

<Callout kind="note" title="The engine stays headless.">
  `overlays()` returns data, never JSX. The same node works in a React host, a
  plain DOM host, or with no UI at all.
</Callout>

<h2 id="sideways-scroll">Content wider than the page</h2>

The page only scrolls up and down. A block that is wider than the page, such as a table with many columns, scrolls sideways on its own. The engine sends it the sideways gestures: a trackpad swipe, Shift + wheel, or a finger drag that starts out sideways.

Three optional methods turn this on:

```ts
class WideNode extends Node<WideBlock> {
  // Is there content past the sides right now?
  canScrollSideways(c) {
    return contentWidth(this.layout(c)) > c.maxWidth;
  }

  // Move by deltaX px (positive shows more on the right). Return null at the
  // end, so the gesture goes to the page.
  scrollSideways(c, deltaX) {
    const max = contentWidth(this.layout(c)) - c.maxWidth;
    const now = scrollOf(c.state, c.block.id);
    const next = Math.max(0, Math.min(max, now + deltaX));
    return next === now ? null : withScroll(c.state, c.block.id, next);
  }

  // Scroll so the caret at `point` shows. Return null when it already does.
  revealSideways(c, point) {
    const now = scrollOf(c.state, c.block.id);
    const next = scrollThatShows(this.layout(c), point, now);
    return next === now ? null : withScroll(c.state, c.block.id, next);
  }
}
```

Keep the offset in `c.state.ui.nodeViewState[c.block.id]`. It belongs to this device only, like the page scroll, so it is never saved or synced. Changing it repaints the block.

Your node does the rest: paint with the offset, clip at the page edge, and map clicks and carets through it.

**A caret scrolled out of sight.** Do not return `null` from `contentCaretRect`. Return the rect with `x` pinned to the edge it is past, and `offscreen: "left"` or `"right"`. The editor then hides your own caret, and shows a small pill at that edge for a collaborator's. Tapping the pill calls `revealSideways`.

**Two extras.** `paint` gets `c.viewport`, so a scrollbar can stay on screen while the block runs past the edge. And a touch that starts on a block that can scroll sideways belongs to the editor (see `editor.host.ownsPointerGesture()`), so a host's page swipe does not take it.

<h2 id="mark">mark (inline)</h2>

A mark is inline formatting such as bold, a link or a highlight. How much you hand to `defineMark` decides how much the mark can do.

With only a name, the mark is saved and synced to other peers, but it paints as plain text and is dropped on markdown export:

```ts
import { defineMark } from "@tasfer/editor";

const highlight = defineMark("highlight");
```

To see it on the canvas, write a `Mark` subclass. Its `style()` returns the paint:

```ts
import { Mark } from "@tasfer/editor";

class HighlightMark extends Mark {
  readonly type = "highlight";
  style() {
    return { background: { color: "#fde68a", padding: 2, borderRadius: 3 } };
  }
}
```

Then pass it as `render`. Add a `codec` as well, and the mark gets its markdown delimiters (`==text==`) and an HTML tag, so it survives export and import:

```ts
const highlight = defineMark("highlight", {
  render: new HighlightMark(),
  codec: highlightCodec,
});
```

<h3 id="selection-wrap">Wrap a selection by typing</h3>

A mark can also wrap a selection when you type its character, the way VS Code wraps a selection in quotes. Select some text, type `=`, and the text is highlighted instead of replaced. Declare it with `selectionWrap`:

```ts
class HighlightMark extends Mark {
  readonly type = "highlight";
  readonly selectionWrap = [{ char: "=" }];
  style() {
    return { background: { color: "#fde68a", padding: 2, borderRadius: 3 } };
  }
}
```

The built-in marks already do this: `` ` `` gives code, `~` gives strikethrough, and the optional math extension adds `$` for inline math.

Two marks can share one character if you give them different `level`s. Each press then steps to the next one. Emphasis (`*`, level 1) and strong (`*`, level 2) work this way: _em_ → **strong** → **_both_** → plain.

<h3 id="caret-edge">The caret at a mark's edge</h3>

Where a mark starts or ends, one spot on screen is two places to type: with the text before it, or with the text after it. The caret shows which one with a small flag at its top, pointing to the side your typing goes to. The arrow keys step between the two before moving on.

Ordinary marks get this for free. A mark with its own caret stops, like an inline formula, answers `caretEdgeFlag(state)` instead. Return `"left"` or `"right"` when the caret is on one of its edges, and `null` when it is not. It runs every time the caret is drawn, so keep it cheap.

<h2 id="register">Register them</h2>

`extend` returns a new schema. The base is never changed, so two editors on one page can use different schemas.

```ts
import { createEditor, baseSchema } from "@tasfer/editor";

const schema = baseSchema.extend({
  nodes: [callout],
  marks: [highlight],
});

const editor = createEditor({ element, schema });

// Saving and markdown keep the custom block:
editor.getMarkdown(); // …  <x-callout tone="warn" />  …

// TypeScript knows your types in every editor call:
editor.change((c) => {
  c.insertBlock({ type: "callout", tone: "note" });
  c.setBlock({ type: "callout", tone: "warning" });
  // c.setBlock({ type: "calluot" }); // TypeScript error
});

const block = editor.query.block();
if (block?.type === "callout") {
  block.attrs.tone; // inferred from defineNode
}
```

Two more things live in the reference, because most nodes never need them:

- Your own markdown syntax: `markdownSyntax` on [`defineNode`](/docs/editor/api-schema#definenode) and [`defineMark`](/docs/editor/api-schema#definemark).
- Marks whose content lives in an attachment, like an inline formula: [Marks inside structured content](/docs/editor/api-schema#structured-marks).

<Callout kind="tip" title="Schema changes are CRDT-safe.">
  Blocks are stored by type *name*, so a peer on the same schema merges your
  callouts cleanly. A peer *without* the type does not crash or lose data. It
  keeps the block and shows an "unsupported block" placeholder until it
  upgrades. Ship schema changes to all peers together, like a database
  migration.
</Callout>

To limit which types an editor may _create_ (a one-line title, a comment box), use [`restrict`](/docs/editor/api-schema#restrict). It only blocks creating: the editor still shows a `callout` that a collaborator or a paste brings in.
