<h2 id="marks">Core inline marks</h2>

<h2 id="math">Optional math</h2>

Math is a feature, not a core node type. It ships as its own package,
`@tasfer/math`, which owns the `@tasfer/tex` layout engine — nothing in
`@tasfer/editor` imports either, so hosts that do not need formulae pay no math
dependency or authoring cost. Install display math (`$$…$$`) and inline math
(`$…$`) together:

```bash
npm install @tasfer/editor @tasfer/math @tasfer/tex
```

```ts
// appDataSchema.ts — safe to import from workers and persistence code
import { baseDataSchema } from "@tasfer/editor";
import { mathDataExtension } from "@tasfer/math/data";

export const appDataSchema = baseDataSchema.extend(mathDataExtension());

// editorSchema.ts — imported only by the interactive editor surface
import { baseSchema, createEditor } from "@tasfer/editor";
import { mathExtension } from "@tasfer/math";

export const appSchema = baseSchema.use(mathExtension());

const editor = createEditor({
  element,
  markdown: String.raw`Euler: $e^{i\pi}+1=0$`,
  schema: appSchema,
});
```

`appSchema` is the canvas/editor half; the independently composed
`appDataSchema` is the worker-safe persistence and serialization half. Each
piece registers once, on the spec that owns it: the math block spec carries its
codec and the `$$…$$` display recognizer, the math mark spec carries the `$…$`
inline recognizer and the structured-mark behavior, and a `structuredKinds`
entry for the shared `"math"` kind carries the snapshot clone adapter. The full
`appSchema` additionally installs the rendering classes, the `"math"` kind's
selection adapters (the clipboard serializer and the range resolver that keeps
committed selections construct-atomic), and the live input rules. Keep the two
definitions paired, but keep their modules separate so a worker importing the
data schema cannot evaluate the interactive graph.

If a worker should not import the interactive math view, compose the data-only
entry there. It registers the specs above — codecs, Markdown syntax,
structured-mark behavior, and the kind's clone adapter — without constructing
`MathNode`, `MathMark`, or the live input/selection stack (the kind's selection
adapters resolve selections through the `@tasfer/tex` layout engine, so they
deliberately belong to the full extension):

```ts
import { baseDataSchema } from "@tasfer/editor";
import { mathDataExtension } from "@tasfer/math/data";

export const workerDataSchema = baseDataSchema.extend(mathDataExtension());
```

Structured `content_edit` operations are schema-agnostic and replay through
this data schema. Interactive editors install the full extension:

```ts
const mathSchema = baseSchema.use(mathExtension());
```

Display and inline editing both use structured `MathDocument` operations.
Every creation path — markdown import, the `$…$`/`$$` input rules, wrapping a
selection, block conversion — creates the structured document immediately; the
tree is the only source of a formula's content.

```ts
import {
  createDoc,
  createEditor,
  parsePage,
  serializeToMarkdown,
  tokenizePage,
} from "@tasfer/editor";

const doc = createDoc({ markdown: savedMarkdown, schema: appDataSchema });
const attachedEditor = createEditor({ element, doc, schema: appSchema });
const page = parsePage(
  tokenizePage(importedMarkdown, appDataSchema),
  appDataSchema,
);
const output = serializeToMarkdown(page.blocks, undefined, {
  schema: appDataSchema,
});
```

Without `mathExtension`, dollar-delimited input remains literal text: the
parser preserves both `$...$` and `$$...$$` source instead of silently
interpreting or discarding it. That lets a math-free client retain content from
a newer or differently configured peer until the feature is installed. In a
math-enabled document an inline equation stores no LaTeX in block characters
at all: the mark anchors on a single object-replacement placeholder character
(U+FFFC) and its content lives wholly in the referenced `MathDocument`
attachment. A display block's flat text is empty; its content is the
block-authority document. A host without the math feature renders the
placeholder glyph.
The feature also exposes `MathDocument`,
`mathDocumentToStructured`, `structuredToMathDocument`, and
`parseMathDocumentInit`; editor core supplies the generic `content_edit`
tree/text CRDT those adapters target. Tree-backed display math owns its block;
tree-backed inline math is a supplemental attachment referenced by the covering
mark. Neither path dual-writes a second editable LaTeX representation.
The two forms convert into each other losslessly: Backspace at a display
equation's leading edge demotes it to an inline chip, and converting a block
whose only content is one inline chip to `math` — `setBlock({ type: "math" })`,
a slash command, or a context menu — promotes the same tree to a display
equation.

<h2 id="code">Optional code rendering</h2>

Code splits differently from math: the **type** is core, the **painter** is not.
`@tasfer/editor` tokenizes ```fences, describes the CRDT shape and owns the
Markdown/HTML/text round-trip, so a document containing code parses, syncs,
serializes and exports with`baseSchema` alone. What lives outside is the
on-canvas node — layout, editing behavior and syntax highlighting — because the
highlighting carries a grammar set far larger than the engine itself:

```bash
npm install @tasfer/editor @tasfer/code
```

````ts
import { baseSchema, createEditor } from "@tasfer/editor";
import { codeExtension } from "@tasfer/code";

const schema = baseSchema.use(codeExtension());
const editor = createEditor({
  element,
  schema,
  markdown: "```ts\nconst x = 1\n```",
});
````

Skip the package and nothing is lost from the document: the block still round-trips
and still replicates, it simply has no painter and renders as the same placeholder
any unregistered block type gets. That is the difference from `mathExtension`,
which registers a block type that core does not otherwise know at all.

The package also exports `CODE_LANGUAGES` and `codeLanguageLabel` (for a language
picker), the `INDENT_CODE` / `OUTDENT_CODE` actions for a toolbar, and
`highlightLine` if you want the tokenizer on its own.

<h2 id="table">Optional tables</h2>

`@tasfer/table` registers the `table` block: a grid of rich-text cells that
round-trips as a GitHub-flavored Markdown table. The block itself stores
nothing — its columns, rows and the text of every cell live in one structured
attachment, so a table merges cell-by-cell and character-by-character rather
than as one opaque value.

```bash
npm install @tasfer/editor @tasfer/table
```

```ts
import { baseSchema } from "@tasfer/editor";
import { tableExtension } from "@tasfer/table";

const schema = baseSchema.use(tableExtension());
```

Headless hosts (workers, Markdown tooling, the CLI) take the canvas-free half
instead, which registers the CRDT shape and the round-trip but no renderer:

```ts
import { baseDataSchema } from "@tasfer/editor";
import { tableDataExtension } from "@tasfer/table/data";

const schema = baseDataSchema.extend(tableDataExtension());
```

The attachment's shape is:

```
root  (kind "table", authority "block")
  ├── slot "columns" → column nodes    { align? }
  └── slot "rows"    → row nodes
         └── slot "cells" → cell nodes { columnId }, textFields { text }
```

**Columns are identity-bearing nodes and each cell names its column.** That is
what lets two people insert a column and a row at the same moment and still
converge: positional cells could not say which column the new row was missing.
The visible consequence is that a table is **not** guaranteed rectangular — a
row can legitimately have no cell for some column yet, which reads as an empty
cell. `readTable` resolves cells by column identity and reports those gaps, so
build on it rather than indexing a row's cells by position.

Because a cell holds ordinary editor text, marks work inside it (see
`markFields` below). Cell content is _inline_ Markdown, matching GFM: `**bold**`
is bold, while `# not a heading` stays literal.

### Markdown shortcuts in cells

Typing `**bold**` in a cell can auto-format the way it does in a paragraph. It
is off unless you ask for it — a table of glob patterns or shell snippets wants
`*` and `` ` `` to stay literal:

```ts
const schema = baseSchema.use(tableExtension({ markdownShortcuts: true }));
```

Hosts assembling a schema by hand build the rule directly, with
`createTableInputRule({ markdownShortcuts: true })` in place of the default
`tableInputRule` export. Both carry the same rule id, so only one can be
installed.

The recognizers are the engine's own (`**bold**`, `*italic*`, `~~strike~~` and
`` `code` ``), and they fire on the keystroke that closes the delimiter — pasted
text is untouched. Backspace, or the first undo, immediately after one takes the
wrap back and leaves the syntax literal, which is how you type `*text*` in a
cell. Only inline syntax applies: block prefixes stay literal in a cell, since a
GFM cell cannot be a heading or a list.

### On the canvas

The grid always fits the block width — the editor scrolls vertically only — so
columns split that width evenly. Only a resize drag makes one column wider than
another: what a cell holds never moves an edge, so typing in a table does not
rearrange it. Cell text wraps inside the width its column already has, and no
column is laid out under `styles.blocks.table.minColumnWidth` — unless the page
is too narrow to give every column even that, where the columns share what
there is rather than run off the page.

Cell text then wraps inside whatever width its column got, and each row takes
the height of its tallest cell — a paragraph in one cell grows that row and
leaves the others alone. When the grid is squeezed so far that even a single
glyph no longer fits its column, the cell clips its own overflow at the
hairline rather than painting across its neighbour.

The caret inside a table is a `ContentPoint` addressing one cell's text field,
never a block text index, so a collaborator editing another cell cannot move
it. Arrow keys step within a cell and cross into the next at its edges, Tab
walks the cells in row-major order, and Enter moves down a row rather than
splitting the block (a GFM cell holds a single line). The vertical arrows also
enter the table from the block above or below and leave it at its edge rows.

Selecting works the same way in cell addresses. Shift with any of those keys
grows a range from wherever the caret was anchored, a double-click (or
double-tap) takes the word under it and a triple-click the whole cell, and a
drag sweeps from the press. A range inside one cell highlights the characters
it covers, exactly as prose does; a range that spans cells covers each of them
whole, because a partial band across a grid reads as a rendering error and
whole cells are the unit the clipboard, the mark toggles and the deletes all
work in. At the grid's first and last stop the keys stay claimed and the range
simply stops growing — a nested range and a flat one are different models, and
there is no half-nested selection to hand the rest of the document.

Copying a range inside one cell puts its characters on the clipboard; across
cells it puts the covered cells, tab-separated within a row and newline
separated between rows, which is the grid convention a spreadsheet reads. That
projection is the kind's `contentSelection` adapter, and — like math's — it is
installed by `tableExtension()` only: a worker replaying operations never holds
a selection. Hosts assembling a schema by hand add `tableContentSelectionKind`
to their `structuredKinds`.

The deletes a cell answers to are the ones every other text surface does:
Backspace and Delete, their word-wise variants (Alt/Ctrl+Backspace,
Alt/Ctrl+Delete) and the line-wise ones (Cmd+Backspace, Cmd+Delete and Ctrl+K
on macOS), which reach the cell's own edges since a GFM cell holds one line.
They break words where the prose beside the table breaks them, and none of them
crosses out of the cell: at an edge the key stays claimed and does nothing.

Deleting the table from inside it takes two presses, as it does for a block
equation: Backspace at the very start of the first cell selects the table whole
— painted with the `blocks.table` `selectionOpacity` wash — and the next press
deletes it. Ctrl/Cmd+A climbs the same container one rung per press: first the
caret's own cell, then the table whole, then — because holding the table clears
the nested caret — the whole document. A press that could not widen skips a
rung, so a selection already spanning two cells, or a caret in an empty one,
holds the table straight away. Backspace at the start of any other cell stays
inert: cells are a grid, not a text stream, so the key never merges two of them.

The header row is not painted apart from the rest: every row carries the same
background and the same weight, so the grid reads as plain cells. That is
appearance only — structurally `rows[0]` is still the header, which is what
GFM's title line and an HTML export's `<th>` are written from, and what the
insert-above rule below protects.

Appearance is the `blocks.table` theme leaf — `borderColor`, `borderWidth`,
`borderRadius`, `cellPaddingX`,
`selectionOpacity`, `resizeEdgeColor` / `resizeEdgeWidth` for the column edge
under the pointer, plus the
`TextStyle` fields every cell's prose uses. Like `blocks.code`, it resolves
from the theme tokens, so a table follows a host's palette and dark mode
without the feature shipping its own colors.

### Rows, columns and alignment

Structural edits are dispatched actions, addressed to the cell the caret is in
(pass `rowIndex` / `columnIndex` to target another cell, and `blockId` to target
another table — an on-canvas control acts on the grid under the pointer, which
need not be the one the caret is in):

```ts
import {
  TABLE_INSERT_ROW,
  TABLE_DELETE_ROW,
  TABLE_INSERT_COLUMN,
  TABLE_DELETE_COLUMN,
  TABLE_MOVE_COLUMN,
  TABLE_SET_COLUMN_ALIGN,
} from "@tasfer/table";

editor.dispatch(TABLE_INSERT_ROW, { side: "after" });
editor.dispatch(TABLE_SET_COLUMN_ALIGN, { align: "right" });
// `to` is where the column ends up, counted in the grid as it is now.
editor.dispatch(TABLE_MOVE_COLUMN, { to: 0 });
```

Each emits ordinary `content_edit` operations against the attachment, so a
structural edit merges, syncs and undoes exactly like a typed character. Two
commands are refused rather than approximated: removing the last row or column
(a grid with nothing in it has nowhere to put a caret), and inserting a row
above the header, which GFM cannot write. A refused command changes nothing —
a host's cue to disable the control.

Two of those commands also have an on-canvas route. A mouse resting past the
grid's right edge, or in the block's bottom margin, lights a band with a plus in
it; clicking adds a column after the last one, or a row after the last, and
lands the caret in the cell it just made. Like the resize bands these are a
`Node.regions` hit region declaring its own `hover`, so the band that lights up
is the one a click would take.

Only those two edges carry a strip. The left gutter is the block-reorder grab
band, which spans every block's full height, and there is no row to add above
the grid — GFM writes the first row as the column titles, so a row before them
is the position `insertRow` refuses. The strips are mouse-only: hover is what
reveals them, and both sit where a thumb rests while scrolling past a table.

The top margin carries the column-move grips instead. A mouse resting there,
above a column, lights that column and takes the `grab` cursor; dragging
sideways carries it along the grid, which redraws in the order the drop would
produce. That preview is painted from the same layout with the columns
re-ordered (`previewColumnMove`) — the document is not touched, so there is
nothing to undo if the drag is cancelled, and a remote edit landing mid-drag
folds into the real document rather than a copy. The release dispatches
`TABLE_MOVE_COLUMN` — one `node_move` of the column node, since every cell
names its column by id and comes along by construction. A column dropped back
beside itself is a no-op, and Escape cancels the drag (as it does any region
drag holding the pointer). The grip is mouse-only for the same reason the
strips are; a phone reaches the move through the two commands in its keyboard
toolbar's table menu.

To label and enable that control, read the grid at the caret with
`tableShapeAt(document, point)`, which returns `{ rows, columns, rowIndex,
columnIndex, align }` from the same public currency a host already holds —
`query.content()` and `state.contentSelection`.

Converting a block to `table` creates a blank 3×3 grid with the caret in its
first header cell. The feature claims `CONVERT_STRUCTURED_BLOCK` to do it: a
generic morph would leave a `table` block with no attachment, which paints as
nothing.

### Column widths

Dragging an interior column edge (a `Node.regions` hit region on the node)
trades width between the two columns it separates. The outer edges are not
draggable — the grid is always exactly as wide as the page, so they have
nowhere to go, and keeping the pair's total fixed means no other column moves.
On touch the drag arms behind a short hold (`touchHoldMs`), so a scroll or a
long-press selection beginning near a column edge is never stolen.

A mouse resting on an edge lights it up and takes the `ew-resize` cursor. The
region declares that affordance itself (`hover` on the hit region, recorded in
`ui.regionHover`), so the lit edge is by construction the one a press would
grab; it stays lit for the length of the drag.

A resized column stores its width as a **fraction** of the grid rather than a
pixel count: the same document opens on a phone and a desktop, and a stored
pixel width would be wrong on one of them. Untouched columns stay
content-sized — never squeezed below the widest word they have to show. A
column someone dragged is exactly as wide as they dragged it, down to
`minColumnWidth`, and wraps or clips its text to suit. A stored width still
yields when it would starve an untouched neighbour below that floor. The
drag itself writes no operations until release, so a gesture costs one entry in
the log rather than one per frame.

Widths are presentation, not content — they live on the column node and never
reach the Markdown.

<h2 id="structured-marks">Marks inside structured content</h2>

A structured node's `textFields` are the same character CRDT block text uses,
and a node may carry `markFields` — inline marks over those fields, keyed by the
same field name. That is what makes rich text inside a table cell (or any other
structured node) possible.

```ts
import { getStructuredMarks, resolveMarkRunsFromChars } from "@tasfer/editor";

// One `mark_set` structured edit, carried by an ordinary content_edit op:
const edit = {
  kind: "mark_set",
  nodeId: cell.id,
  field: "text",
  charIds, // a contiguous document-order run of the field's char ids
  mark: { type: "strong" },
  value: true,
};
```

To let a user _apply_ one of those marks, claim `TOGGLE_MARK`. It is the single
action every mark toggle funnels through — Ctrl/Cmd+B, the mobile toolbar, the
desktop Format menu, and `editor.change(c => c.setMark(name))` — and it carries
the mark as a name, so one handler covers bold, italic, strike and code at once:

```ts
import { TOGGLE_MARK } from "@tasfer/editor";

bus.registerState(
  TOGGLE_MARK,
  (state, { name }) => {
    const context = activeContext(state);
    return context ? toggleMarkInMyNode(state, context, name) : undefined;
  },
  100,
);
```

Return `undefined` when the caret is elsewhere and the ordinary flat-text path
runs unchanged. At a collapsed caret, set `ui.activeMarksMode` to
`{ type: "explicit", formats }` rather than writing an edit, and apply those
formats to the characters your insert path adds next — that is what makes
"Ctrl+B, then type" come out bold inside a cell. Marks active on a nested
selection are reported by `editor.state.activeMarks` for free.

The spans anchor to character identities, so a mark survives edits inside its
range and merges per character. Unlike a block's `formats`, they carry no HLC:
structured edits fold in canonical op-log order, so the last write already wins.
Read them with `getStructuredMarks(document, nodeId, field)` and resolve them
with the same `resolveMarkRunsFromChars` the block path uses.

Two more helpers matter once a structured document gets large enough to walk:

- `buildStructuredChildIndex(document)` resolves every parent/slot's children
  once; pass it as `getStructuredChildren(…, { index })`. Without it each lookup
  scans the whole document, which is fine for a formula and quadratic for a grid.
- `cloneStructuredDocumentWithFreshIdentities(…, { rewriteAttrs })` re-points
  identity-bearing attrs when a snapshot mints new ids. A kind that stores a node
  reference in an attr (a table cell's `columnId`) must supply this, or the copy
  references identities that no longer exist.

<h2 id="extend">Extending</h2>

`use` installs a reusable feature bundle. Feature objects can contribute nodes,
marks, structured-kind adapters, live-input rules, action hooks, and theme or
string defaults. Markdown syntax recognizers and structured-content behavior
are not feature keys: they ride the node and mark specs themselves
(`markdownSyntax` on both, `structured` on marks), so each type registers once
with everything it owns. All facets are immutable and scoped to the resulting
schema, so two editors can install different feature sets on the same page:

```ts
import {
  baseSchema,
  defineMark,
  defineNode,
  type FeatureExtension,
} from "@tasfer/editor";

export const calloutFeature = {
  name: "callouts",
  nodes: [defineNode("callout", { attrs: { tone: { default: "note" } } })],
  marks: [defineMark("highlight", { attrs: { color: { default: "yellow" } } })],
} as const satisfies FeatureExtension;

const schema = baseSchema.use(calloutFeature);
```

Use `as const satisfies FeatureExtension` for exported feature values: it
checks the public feature contract while retaining literal node, mark, and
attribute types for the resulting `Editor` API. The optional `name` is metadata,
not a deduplication key; calling `use` twice composes twice, with the same
later-definition-wins behavior as `extend`.

For one-off registration, `extend` remains the lower-level API. It takes
_arrays_ of node and mark specs and returns a new, immutable schema:

```ts
const oneOffSchema = baseSchema.extend({
  nodes: [defineNode("one_off")],
});
```

Both methods leave the base untouched, so two editors on one page can run
different schemas. The schema's type is inferred and carried through `Doc`,
`Editor`, the React bindings, `ChangeApi`, and `query`; you do not pass a generic
manually:

```ts
const editor = createEditor({ element, schema });

editor.change((c) => {
  c.setBlock({ type: "callout", tone: "note" });
  c.setMark("highlight", { attrs: { color: "orange" } });

  c.setBlock({ type: "calluot" }); // TypeScript error: unknown block
  c.setMark("higlight"); // TypeScript error: unknown mark
});

const block = editor.query.block();
if (block?.type === "callout") {
  block.attrs.tone; // string
}
```

<h2 id="restrict">Restricting (allowed types)</h2>

`use` and `extend` decide which types _exist_. `restrict` decides which of them
the local user may _author_ — the ProseMirror-style allow-list. It returns a new
immutable schema, leaves the full registry (and therefore rendering) untouched,
and is the tool for constrained fields like a single-line title or a plain-text
comment box:

```ts
// A title field: the user can only ever produce a heading1, with no inline marks.
const titleSchema = baseSchema.restrict({ blocks: ["heading1"], marks: [] });
const title = createEditor({ element, schema: titleSchema });
```

- Omit a key to leave that dimension unrestricted; `marks: []` is a genuinely
  format-free field. Every name must already be registered (apply `use` /
  `extend` first, `restrict` last).
- The `paragraph` fallback is **always** creatable and cannot be excluded, so a
  document can never become unrepresentable — you never need to list it.
- The default `baseSchema` is unrestricted: without a `restrict` call every
  registered type is authorable, exactly as before.
- A third key, [`content`](#content), constrains the document's _shape_ — the
  order and count of its blocks — rather than which types exist.

**Authoring vs. rendering.** `restrict` gates _creation only_. Slash/menu
conversions, Enter-splits, Markdown shortcuts (`# `, `- `), paste, and
`change` API calls that would mint a disallowed type are refused (no-op) or
coerced to a plain paragraph; disallowed marks (`setMark`, the
`**bold**` shortcut) no-op. But a restricted editor still **renders** a
disallowed-but-registered block that arrives some other way — pasted, imported,
or synced from a collaborator on a looser schema. Paste and import are
normalized to the allow-list (a disallowed heading pastes as text; an image
drops); already-synced document content is not rewritten.

**Collaboration is safe.** The allow-list is an authoring constraint, never a
storage one — the CRDT log and the reducer ignore it entirely. Two peers with
_different_ allow-lists (say a locked title field and a full body) still
converge: the allow-list only governs what a peer can mint, never how it renders
the shared log. See [Collaboration](/docs/editor/collaboration).

```ts
const restricted = baseSchema.restrict({ blocks: ["heading1"], marks: [] });

// Query the allow-list to gate your own toolbar / slash menu chrome:
restricted.data.isBlockAllowed("bullet_list"); // false
restricted.data.isMarkAllowed("strong"); // false
restricted.data.hasBlock("bullet_list"); // true — still registered, still renders
```

<h2 id="content">Document shape (content expressions)</h2>

`blocks` and `marks` say which types the user may author. `content` says in what
**order** and **how many** — a ProseMirror-style content expression over the
document's flat block sequence:

```ts
// A brief: one title, then at least one paragraph of body.
const briefSchema = baseSchema.restrict({ content: "heading1 paragraph+" });

// A card: a title and up to three body blocks, paragraphs or images.
const cardSchema = baseSchema.restrict({
  content: "heading1 (paragraph|image){1,3}",
});

// A titled page: one heading, then anything.
const pageSchema = baseSchema.restrict({ content: "heading1 block*" });
```

**Grammar.** A sequence of names, with alternation `|`, grouping `(…)`, and the
repetitions `+` (one or more), `*` (zero or more), `?` (optional), `{n}`,
`{n,}` and `{n,m}`. Whitespace separates names and is otherwise insignificant.

**Names.** Either a registered block type or a **group**. Groups are derived
from each registered type's capabilities, so there is no group table to
maintain:

A custom type joins extra groups of its own with `defineNode(type, { groups })`,
so a family of related types can be addressed as one (`"heading1 card+"`).

**Enforcement is the same authoring contract as the allow-list.** An edit that
would leave the document unable to satisfy the expression is refused, and the
check is applied where an edit commits rather than inside each command — so it
covers every gesture, including one a custom node or mark handles itself. A
refused edit is rolled back whole: the key that triggered it does nothing.

Where a command can adapt instead of failing it does. Enter splits into the type
the shape permits, and goes inert only when it permits none; paste is repaired to
the shape _where it lands_. Everything else refuses: a slash/menu conversion, a
Backspace-merge, a delete of a whole-selected block, `change().deleteBlock()`, or
one of the implicit conversions a delete key reaches (a list item demoting to a
paragraph at indent 0, a display equation demoting at its leading edge) all leave
the document as it was. `change()` returns `false` when its batch is refused, and
`canChange()` reports it in advance. A loaded document is repaired as a whole — a
block the shape rejects is demoted to a type it can morph into (text preserved)
or dropped, and a missing tail is appended.

An already-invalid document is never locked. A document synced from a peer on a
looser schema, or stored before you tightened the expression, keeps editing
normally — only edits that turn a _satisfying_ document into a non-satisfying
one are refused.

**The shape is a local authoring guard, not a collaborative invariant.** Each
peer judges an edit against the document it can currently see, so two edits that
are each legal on their own replica can merge into a sequence that is not — under
`"heading1 paragraph+"`, one peer deleting the last paragraph while another
concurrently deletes the first leaves a lone heading, and neither edit was
refusable when it was made. The peers still converge on the same document, and
the rule above keeps it editable. Peers on _different_ schemas reach the same
place more directly: operations are never filtered on receipt (that would break
convergence), so a looser peer's edit applies verbatim on a stricter one.

Read `content` as "the editor will not let a user break this here", not as a
guarantee the document always satisfies it. If your host depends on the shape —
rendering, export, a downstream parser — validate with `contentAccepts` at the
point you depend on it, and treat a document that fails as something to repair
rather than something that cannot happen.

```ts
const shaped = baseSchema.restrict({ content: "heading1 paragraph+" });

// Query the shape to gate your own chrome:
shaped.data.contentAccepts(["heading1", "paragraph"]); // true
shaped.data.contentAccepts(["paragraph"]); // false
shaped.data.contentFill(["heading1"]); // ["paragraph"] — what's still missing
shaped.data.contentTypesAt(["heading1"], 1); // ["paragraph"] — legal here
```

- Every name must already be registered (apply `use` / `extend` first, `restrict`
  last). An unknown name, a malformed expression, or one no document could ever
  satisfy throws at `restrict` time rather than at edit time.
- Pairing `content` with `blocks` is checked: a shape that needs a type the
  allow-list forbids is rejected as unsatisfiable.
- With a `content` expression the automatic `paragraph` fallback is **not**
  forced into the allow-list — the expression already guarantees a document can
  be built, and a shaped schema shouldn't advertise a paragraph its own shape
  would refuse.
- Collaboration is safe on the same terms as the allow-list: the CRDT log and the
  reducer never read the expression, so peers on different shapes converge.

<h2 id="window">View windows (title surfaces)</h2>

`restrict` decides which types an editor may author; a **view window** decides
which of a document's _blocks_ an editor renders and edits. Pass one as the
`window` option to `mountEditor` / `createEditor` / `useEditor`. Omit it (the
default) for a full-document editor.

A window's headline use is a **title editor**: a second, compact surface bound to
the _same_ `Doc` as the main body, scoped to just the title block. Because both
editors share one CRDT document, editing the title updates the body's heading
live — with no extra sync wiring (collaboration lives on the doc, not the
surface).

```ts
import {
  createDoc,
  createEditor,
  baseSchema,
  titleBlockWindow,
} from "@tasfer/editor";

const doc = createDoc({
  markdown: "# My page\n\nBody…",
  schema: baseSchema.data,
});

// Full body editor over the whole doc.
const body = createEditor({ element: bodyEl, doc });

// A title editor over the SAME doc — only the title block, only a heading1.
const title = createEditor({
  element: titleEl,
  doc,
  schema: baseSchema.restrict({ blocks: ["heading1"], marks: [] }),
  window: titleBlockWindow(),
});
```

- `titleBlockWindow()` scopes to the document's **title block** — the first
  text-bearing block (heading, paragraph, list, …), skipping leading images or
  dividers. It resolves the block structurally, so the window stays put even when
  the title is momentarily empty. `blockIdWindow(id)` scopes to one specific
  block; `titleBlockIndex(blocks)` returns the title block's index (or `-1`).
- These are **single-block** windows: the surface can never split (Enter is
  inert), merge into a neighbour (Backspace/Delete at the edges no-op), gain
  blocks from a paste (it flattens to inline text), and the caret cannot leave
  the window. It never mutates any block but its own.
- A window is a **view/authoring concern only** — never a storage one. The doc,
  reducer, and sync ignore it, so a windowed and a full editor on one doc always
  converge. Pair it with `restrict` to also constrain the single block's type
  (e.g. "only ever a `heading1`"); the block still _renders_ whatever it already
  is.

`ViewWindow` is the general shape (`{ select, singleBlock? }`) if you need a
custom rule — `select(blocks)` returns the set of original indices to show.
