<h3 id="relay-privacy">What the relay can see</h3>

Edits are encrypted with a key made from your `secret` before they leave the browser. The relay passes them along. It cannot read them, and it cannot change them without that being noticed.

It still sees the room name, who is connected, and the size and timing of every message.

Two things to know:

- Everyone in a room shares one key. So anyone who has the secret can pretend to be someone else in that room.
- `secret: null` turns encryption off, and the relay can then read everything. Only do that on a relay you run yourself.

With `provider-webrtc` the document never goes through a server. Edits go from browser to browser, encrypted, and the signaling server only helps the browsers find each other.

<h2 id="stack">Use several at once</h2>

You can put several providers on one document. A common setup saves locally and syncs over the network:

```ts
import { createIndexedDBProvider } from "@tasfer/provider-indexeddb";
import { createRelayProvider } from "@tasfer/provider-relay";

createIndexedDBProvider({ doc: editor.doc, name: "notes/today" });
const net = createRelayProvider({
  doc: editor.doc,
  room: "team-notes",
  relay: "wss://relay.tasfer.app",
  secret: roomSecret,   // share it with people yourself, never with the relay
});
```

<h2 id="presence">Presence & remote cursors</h2>

Presence is the live information that is not part of the document: who is here, where their caret is, what color they are. It travels with the edits but is never saved. You can publish any object you like:

```ts
net.presence.set({ name: "Ada", color: "#1db984" });

// each entry is { peerId, state }; state is what that person published
net.presence.on("change", (peers) => {
  avatars.render(peers.map((p) => p.state.name));
});
```

The editor itself does not know about other people. It only draws [decorations](/docs/editor/api-editor#decorations): a caret decoration for someone's caret, and a range decoration for their selection. `bindPresenceCursors` connects presence to decorations for you:

```ts
import { bindPresenceCursors } from "@tasfer/provider-core/cursors";

// sends your selection on every change, and draws everyone else's.
// Returns a function that stops it.
const stop = bindPresenceCursors(editor, net, {
  user: { peerId, name: "Ada", color: "#1db984" },
});
```

Each person gets their own decoration layer, named `presence:<peerId>`.

Sending presence over your own transport? Use the two functions underneath. `selectionToCursorPresence(editor.state.selection.range, user)` makes the object to send. `cursorPresenceToDecorations(peerId, state)` turns a received one into decorations for ``editor.view.setDecorations(`presence:${peerId}`, …)``.

<Callout kind="note" title="Offline is not a special case.">Disconnect, edit for an hour on a plane, reconnect. Your changes merge with everyone else's, and everyone ends up with the same document. There is no "resolve conflicts" dialog because there are no conflicts. [Core concepts](/docs/editor/concepts#crdt) explains why.</Callout>

<h2 id="schemas">Peers with different schemas</h2>

Two people editing the same document do not need the same schema. A schema limits what you can *create*, not what you can *see* (see [restricting a schema](/docs/editor/api-schema#restrict)). If your schema only allows headings and someone else adds a bullet list, you still see the list. You just cannot make one yourself.

The same goes for old versions. An older build that does not know a newer block type keeps that block's data, so saving never loses it. It shows the block once its schema learns the type.

If you write your own provider, never filter or drop edits you do not recognize. That is the one thing that makes people's copies drift apart.
